## 1. 전체 흐름

K-System(Flex-K) 연동은 화면 데이터를 ERP DB 의 SP 로 보내고 결과를 다시 화면으로 받는 구조입니다.
화면 이벤트 → 서비스(ksystem, FlexAPI) → [보내는 데이터]가 #BIZ_IN_DataBlock{n} 의 행이 됨 → SP 실행 → SP 가 #BIZ_OUT_DataBlock{n} 에 결과를 씀 → [받는 데이터]로 카테고리에 반영 → 화면
데이터가 이미 ERP 에 있으면 K-System(FlexAPI) 서비스를 쓰세요.
ERP 밖의 새 데이터만 다루면 FlexSQL 이나 FlexDB 를 검토하세요.

## 2. 연동 준비 확인

SP 를 부르기 전에 테넌트의 K-System 시스템 정보가 채워져 있어야 합니다.
1. 콘솔에서 테넌트 회사 정보의 [사용할 System]에 K-System 이 저장돼 있는지 보세요.
2. [시스템 정보]의 K-System 탭을 여세요.
3. Oper dsn, Bis dsn, CompanySeq, FlexK API URL 네 값이 있는지 보세요.

값은 K-System 연동 설치를 마친 뒤 받은 안내의 값을 그대로 넣으세요.
dsn 은 DB 이름이 아니라 서버 쪽 접속 이름입니다.
SP 를 어느 물리 DB 에 만들어야 하는지는 ERP 담당자에게 먼저 확인하세요.
연동 탭은 테넌트당 하나라서, 한 테넌트의 모든 앱은 같은 ERP DB 를 봅니다.

## 3. 서비스 설정 화면 항목

시나리오의 Service 탭에서 서비스를 만들고 아래 값을 넣으세요.

| 화면 항목 | 넣을 값 | 설명 |
|---|---|---|
| [서비스 종류] | ksystem | FlexSQL 과 갈리는 지점입니다 |
| [모듈명] | FlexAPI | 일반 SP 호출입니다 |
| [SP List] | 만든 SP 이름 | 여러 개를 넣으면 적은 순서대로 실행됩니다 |
| [데이터베이스 유형] | [업무] 또는 [운영] | SP 를 만든 DB 에 맞춥니다 |
| [공통 트랜잭션 사용] | 켬 | 11절을 보세요 |
| [TempTable to CREATE in SQL script] | BIZ_IN/OUT_DataBlock | #BIZ_IN·#BIZ_OUT 을 만드는 설정입니다 |
| [TempTable to SELECT in SQL script] | BIZ_IN/OUT_DataBlock 또는 None | 4절을 보세요 |
| [Before Script], [After Script] | 보통 비움 | |

새 서비스를 만들면 CREATE 기본값은 FLEX_DataBlock, SELECT 기본값은 None 입니다.
기본값 그대로 두면 #BIZ_IN·#BIZ_OUT 이 만들어지지 않아 결과가 오지 않습니다.
#BIZ_IN·#BIZ_OUT 을 쓰는 SP 라면 CREATE 를 반드시 BIZ_IN/OUT_DataBlock 으로 바꾸세요.
[데이터베이스 유형]의 [업무]는 Bis dsn, [운영]은 Oper dsn 으로 SP 를 실행합니다. 기본값은 [업무]입니다.

## 4. Q조회와 R조회

[TempTable to SELECT in SQL script] 하나가 결과를 누가 돌려주는지를 정합니다.

| 구분 | SELECT 설정 | SP 가 할 일 | _SUID |
|---|---|---|---|
| Q조회 | BIZ_IN/OUT_DataBlock | #BIZ_OUT 에 INSERT 만 합니다. 마지막 SELECT 를 하지 않습니다 | NEWID() 로 채웁니다 |
| R조회 | None | SP 마지막에 SELECT 로 결과를 돌려줍니다 | 넣지 않습니다 |

두 방식 모두 CREATE 는 BIZ_IN/OUT_DataBlock 입니다.
저장 SP 는 Q조회 설정으로 두세요.
저장 SP 와 조회 SP 를 한 서비스에 묶으면 SELECT 설정이 하나뿐이므로, 조회 SP 도 Q조회 방식으로 써서 저장 SP 와 맞추세요.
결과 키를 [Etc] 탭에 모두 등록하기 어렵거나 이미 마지막 SELECT 로 끝나는 SP 를 쓴다면 R조회를 고르세요(6절).
R조회 결과는 플랫폼이 새 _SUID 를 붙이므로 [받는 데이터]를 [덮어쓰기]로 받으세요.

## 5. 이벤트의 서비스 액션: 보내는 데이터, 사용자 데이터, 받는 데이터

이벤트에 서비스 액션을 넣고 [서비스 종류 : 기존 서비스 사용]에서 만든 서비스를 고르세요.

| 화면 항목 | 하는 일 |
|---|---|
| [보내는 데이터] → [카테고리명] | SP 에 보낼 입력 카테고리입니다. 조회면 조건 카테고리, 저장이면 입력 카테고리입니다 |
| [보내는 데이터] → [사용자 데이터] | 로그인 사용자 정보 키를 행마다 컬럼으로 붙입니다 |
| [보내는 데이터] → [필터설정] | 일부 행만 보냅니다. 비워 두면 카테고리 전체가 갑니다 |
| [받는 데이터] → [카테고리명], [화면에 반영하기] | 결과를 담을 카테고리와 화면 반영 여부입니다 |

[사용자 데이터]에는 CompanySeq, LanguageSeq, UserSeq 를 항상 넣으세요.
이 세 값은 [Etc] 탭 Collections 에 따로 등록하지 않습니다.
로그인 사용자 키(fBaseUserID 등)가 더 필요하면 [사용자 데이터]에 함께 넣으세요.
같은 키를 [사용자 데이터]와 카테고리 키 양쪽으로 보내지 마세요.
EmpSeq 처럼 로그인 정보와 이름이 같은 키는 호출 때 로그인 사용자 값으로 덮어써지므로, 다른 사람의 값은 다른 이름의 키로 보내세요.
조건 칸을 하나도 채우지 않아도 SP 는 호출됩니다.
보낼 행이 없어도 사용자 데이터만 담긴 빈 행 1개가 가기 때문입니다.
SP 에서 빈 조건을 처리하세요(8절).
[필터설정]의 상태 값은 added, updated, deleted, selected, active 등입니다.
체크한 행만 보내려면 이렇게 하세요.
1. 저장 전에 모든 행의 상태를 `setStatus()` 로 비우세요.
2. 체크된 행만 `setStatus('updated')` 를 부르세요.
3. [필터설정]에서 상태 updated 만 보내게 하세요.

[받는 데이터]의 반영 방식은 셋입니다.

| 방식 | 동작 | 쓰는 곳 |
|---|---|---|
| [덮어쓰기] | 기존 행을 모두 지우고 결과로 바꿉니다 | 조회 |
| [추가] (기본값) | 결과 행을 뒤에 붙입니다 | 누적 표시. 조회에 쓰면 행이 계속 늘어납니다 |
| [병합] | 기준 키(기본 _SUID)로 같은 행을 찾아 고치고, 없으면 붙입니다 | 저장 뒤 그 행만 돌려받을 때 |

[병합]의 기준 키를 빈 목록으로 남기면 기본값 _SUID 가 쓰이지 않아 같은 행이 두 줄로 붙습니다.
기준 키를 지우거나 _SUID 를 직접 넣으세요.
[화면에 반영하기]의 자동 갱신은 카테고리가 최상위 그룹에 연결됐을 때만 됩니다.
안쪽 그룹이면 서비스 액션 뒤에 스크립트 액션을 하나 더 두고 `f.Content('<그룹 fid>').reload()` 로 그 그룹을 다시 그리세요.
결과 컬럼은 카테고리 키에 없어도 컬렉션에 담깁니다.
화면에 보이려면 SP 결과 컬럼 이름이 컬렉션 키와 대소문자까지 같아야 합니다.
SP 에서 `AS <컬렉션키>` 별칭으로 맞추세요.

## 6. #BIZ_IN·#BIZ_OUT 임시 테이블 규격

[보내는 데이터] 블록 하나마다 #BIZ_IN_DataBlock{n} 과 #BIZ_OUT_DataBlock{n} 한 쌍이 생깁니다.
SP 를 실행하기 전에 #BIZ_OUT 에는 #BIZ_IN 행이 그대로 복사돼 있습니다.

임시 테이블 컬럼은 세 묶음입니다.

| 묶음 | 컬럼 | 타입 |
|---|---|---|
| 플랫폼 관리 | WorkingTag | NVARCHAR(1) |
| 플랫폼 관리 | IDX_NO, DataSeq, Selected, MessageType, Status, ROW_IDX | INT |
| 플랫폼 관리 | IsChangedMst | NCHAR(1) |
| 플랫폼 관리 | Result, TABLE_NAME | NVARCHAR(255) |
| 플랫폼 관리 | _SUID, _mSUID | NVARCHAR(MAX) |
| 업무 데이터 | 실제로 보낸 값의 키 + [Etc] 탭 Collections 에 등록한 키 | 7절 규칙 |
| 사용자 정보 | [사용자 데이터]에 넣은 키 | 값 모양으로 정해집니다(숫자는 INT 또는 DECIMAL(19,5), 문자는 값 길이에 맞춘 NVARCHAR). 회사, 언어, 사용자는 파라미터로 읽고, 그 밖의 키는 SP 에서 CONVERT 로 타입을 맞추세요 |

#BIZ_OUT 은 #BIZ_IN 과 똑같은 컬럼으로 만들어집니다.

컬럼은 카테고리 키 목록으로 만들어지지 않습니다.
값이 비어서 보내지 않은 키는 컬럼 자체가 생기지 않습니다.
SP 가 읽는 키는 [Etc] 탭 Collections 에 타입과 함께 등록하세요.
등록하면 값이 없어도 NULL 컬럼이 생깁니다.
Q조회 SP 가 #BIZ_OUT 에 넣을 결과 키도 [Etc] 탭 Collections 에 타입과 함께 등록하세요.
등록하지 않은 결과 키에 INSERT 하면 Invalid column name 오류가 납니다.
R조회는 SP 의 SELECT 결과를 그대로 돌려주므로 결과 키를 등록하지 않아도 됩니다.
섹터에 남은 임시 키도 컬럼으로 함께 갑니다.
호출 전에 쓰지 않는 키를 정리하세요.
카테고리 키 이름 규칙입니다.
1. 영문, 숫자, 밑줄로만 지으세요. 키 이름이 그대로 SQL 컬럼 이름이 됩니다.
2. Status, Result, Message, Selected, DataSeq, IDX_NO, ROW_IDX, WorkingTag, TABLE_NAME 은 대소문자와 관계없이 쓰지 마세요.
3. 2번 이름의 값은 SP 로 가지 않고 조용히 사라집니다. 업무 상태는 ApprStatus, OrderState 처럼 이름을 바꾸세요.

## 7. 화면 값이 SQL 타입이 되는 규칙

[Etc] 탭 Collections 에 등록한 타입이 값 모양보다 우선합니다.

| 등록 타입 | 임시 테이블 컬럼 | 값이 들어가는 모양 |
|---|---|---|
| string, size 1~4000 | NVARCHAR(size) | N'값', 작은따옴표는 두 번 겹칩니다 |
| string, size 비움 또는 4000 초과 | NVARCHAR(MAX) | 위와 같습니다 |
| int | INT | 숫자 그대로 |
| double | DECIMAL(19,5) | 숫자 그대로 |

타입을 비우면 문자열로 처리돼 Seq 키도 NVARCHAR(MAX) 가 됩니다.
값이 없으면 NULL 로 들어갑니다.
숫자 타입 키에 빈 문자열이 오면 NULL 이 아니라 0 이 들어갑니다.
"입력 안 함"과 0 을 구분해야 하면 그 키를 string 으로 등록하고 SP 에서 '' 와 비교하세요.
size 는 SP 가 쓰는 컬럼 타입 길이와 맞추는 것이 안전합니다.
사진을 Base64 문자열로 키에 담아 보내면 값이 SQL 문장에 그대로 들어가 요청이 커지고, 약 4MB 를 넘으면 실패할 수 있습니다.
사진은 파일 서비스로 올리고 SP 에는 첨부 번호만 보내세요.

## 8. SP 작성 규칙

FlexAPI 는 SP 를 항상 파라미터 4개로 부릅니다.

```sql
@WorkingTag NVARCHAR(10) = '', @CompanySeq INT = 1, @LanguageSeq INT = 1, @UserSeq INT = 0
```

다른 값은 파라미터가 아니라 #BIZ_IN_DataBlock{n} 의 컬럼으로 옵니다.
파라미터마다 기본값을 꼭 주세요.
ERP 표준 SP 처럼 파라미터가 더 있으면, 더 있는 파라미터에도 기본값이 있어야 합니다.
@xmlDocument 가 필요한 ERP 표준형 SP 는 [SP List]에 바로 넣을 수 없습니다.
임시 테이블을 직접 읽는 SP 를 새로 만드세요.
SP 를 다 쓴 뒤 아래를 하나씩 대조하세요.
1. 파라미터는 4개이고 모두 기본값이 있습니다.
2. 조건은 #BIZ_IN_DataBlock{n} 에서 SELECT 하고 ISNULL 로 빈 값을 처리합니다.
3. 빈 조건은 `(@값 = '' OR 컬럼 = @값)` 처럼 "비면 조건 없음"으로 씁니다.
4. Q조회는 결과 INSERT 전에 `DELETE FROM #BIZ_OUT_DataBlock{n}` 으로 복사된 입력 행을 지웁니다.
5. Q조회 결과 행마다 `_SUID = CONVERT(NVARCHAR(50), NEWID())` 를 채우고 ROW_IDX 는 ROW_NUMBER() 로 채웁니다.
6. Q조회 SP 는 마지막 SELECT 를 하지 않습니다. R조회 SP 만 마지막 SELECT 를 합니다.
7. SP 안에서 임시 테이블을 CREATE 하거나 DROP 하지 않습니다.
8. SP 안에서 BEGIN TRAN 을 쓰지 않습니다. 트랜잭션은 바깥에서 열고 닫습니다.
9. 읽는 테이블마다 `WITH(NOLOCK)` 을 붙입니다. ISOLATION LEVEL 변경은 관례가 아닙니다.
10. 결과 컬럼 이름과 타입이 [받는 데이터] 카테고리 키와 1:1 로 같습니다.
11. 오류는 INT 타입 Status 와 Result 로 알립니다(10절).
12. 회사와 사용자는 @CompanySeq, @UserSeq 파라미터로 읽습니다.

파라미터 @WorkingTag 는 보통 빈 값으로 옵니다.
추가, 수정, 삭제는 파라미터가 아니라 각 행의 WorkingTag 컬럼(A, U, D)으로 가르세요.

## 9. WorkingTag 결정 규칙

WorkingTag 는 직접 쓰는 값이 아니라 행(섹터) 상태가 바뀐 결과입니다.
플랫폼은 삭제, 추가, 수정 순서로 정하고 나머지는 모두 U 로 보냅니다.

| 행을 만든 방법 | 행 상태 | WorkingTag |
|---|---|---|
| 시트 빈 행에 입력, 데이터연결의 새 섹터 | added | A |
| 서비스로 받아온 행(조회 결과) | 비어 있음 | U |
| 스크립트 `f.Collection.addSector(...)` 로 만든 행 | 비어 있음 | U |
| 위 행을 `set()` 이나 시트 편집으로 고침 | updated, 원래 added 면 added 유지 | added 면 A, 아니면 U |
| 저장된 행을 `섹터.delete()` 또는 시트 행 삭제 | deleted | D |
| 저장 전 새 행을 `섹터.delete()` | 메모리에서 사라짐 | 보내지 않음 |
| `f.Collection.removeSector(...)` 로 지운 행 | 메모리에서 사라짐 | 보내지 않음 |

지킬 규칙입니다.
1. 스크립트로 만든 새 행을 저장하려면 서비스 호출 전에 `setStatus('added')` 를 부르세요.
2. `setStatus` 인자는 소문자 'added', 'updated', 'deleted' 셋 중 하나를 정확히 쓰세요. 'Updated', 'A' 처럼 쓰면 상태가 지워지기만 해 U 로 갑니다.
3. DB 에서도 지워야 하는 행은 `섹터.delete()` 로 지우세요. `f.Collection.removeSector` 는 화면 메모리에서만 버립니다.
4. 새로 추가했다가 바로 삭제 표시한 행도 D 로 갑니다. 저장 SP 의 D 처리에서 없는 행 삭제가 오류가 되지 않게 하세요.
5. 상태는 added, updated, deleted 세 가지뿐입니다. 다른 구분(예: X)이 필요하면 별도 컬렉션 키를 만들어 관리하세요.
6. 값은 `섹터.set('<키>', <값>)` 으로 바꾸세요. 직접 대입하면 updated 가 찍히지 않아 필터에서 빠집니다.

## 10. Status·Result 규약

오류는 해당 행의 Status 에 0 이 아닌 정수를, Result 에 메시지를 넣어 알립니다.

| Status | 뜻 |
|---|---|
| 0 또는 NULL | 정상 |
| 0 이 아닌 INT | 오류. 공통 트랜잭션이 켜져 있으면 전체를 되돌리고 화면에 Result 를 보여 줍니다 |
| 999999 | 이 행은 정상이지만 같은 호출의 다른 행이 실패해 전체를 되돌렸습니다 |
| 999998 | 다른 행이 실패했지만 공통 트랜잭션이 꺼져 있어 되돌리지 않았습니다 |

Status 는 플랫폼이 숫자로 비교하므로 'OK', 'ERR' 같은 문자를 넣지 마세요.
Result 는 NVARCHAR(255) 라 255자 안으로 쓰세요.
999999 나 999998 만 보이면 진짜 원인은 다른 숫자가 들어 있는 행의 Result 에 있습니다.
플랫폼은 SP 가 끝날 때마다 모든 #BIZ_OUT 블록의 Status 를 검사합니다.
#BIZ_OUT 에는 입력 행이 복사돼 있으므로, 저장 SP 는 그 행을 UPDATE 해서 Status 와 Result 를 남기면 됩니다.
서비스가 오류로 끝나면 같은 이벤트의 뒤 액션은 실행되지 않습니다.
검사 SP 와 저장 SP 를 나누면 검사에서 오류가 날 때 저장이 실행되지 않습니다.

## 11. 공통 트랜잭션과 SP 여러 개

[SP List]에 SP 를 여러 개 넣으면 적은 순서대로 실행됩니다.
SP 하나가 오류를 남기면 그 뒤 SP 는 실행되지 않습니다.

| 상황 | [공통 트랜잭션 사용] 켬(기본) | 끔 |
|---|---|---|
| SP 가 Status 오류를 남김 | 앞 SP 의 변경까지 모두 되돌립니다 | 앞 SP 의 변경이 남습니다 |
| SQL 실행 오류 | 되돌린 뒤 오류를 화면에 올립니다 | 되돌릴 것 없이 오류를 올립니다 |
| 정상 행 표시 | 999999 | 999998 |

저장 SP 를 여러 개 잇는다면 공통 트랜잭션을 켜 두세요.
저장 SP 뒤에 다시 조회가 필요하면, 이벤트에서 서비스를 두 번 부르지 말고 한 서비스의 [SP List]에 저장 SP 와 조회 SP 를 차례로 넣는 방식을 권합니다.
연결이 한 번으로 끝나 연속 호출 중 연결이 끊기는 문제를 피할 수 있습니다.
처리 시간이 수십 초를 넘는 작업은 시간 제한에 걸릴 수 있으니 나누세요.

## 12. 블록이 여러 개일 때

[보내는 데이터] i번째, #BIZ_IN/OUT_DataBlock{i}, [받는 데이터] i번째가 한 짝입니다.
카테고리 하나가 블록 하나입니다.
조회 조건과 결과 목록은 서로 다른 카테고리로 나누세요.
1. 받을 블록이 N개면 보내는 블록도 N개 두세요. 입력이 필요 없는 블록도 빈 블록을 하나 붙이세요.
2. 설정이 빈 블록은 건너뛰어져 뒤 번호가 앞당겨집니다. 블록마다 최소 설정을 두세요.
3. IDX_NO 와 DataSeq 는 블록마다 1부터 다시 셉니다. 마스터 블록과 디테일 블록을 IDX_NO 로 잇지 말고 업무 키로 이으세요.

## 14. 막혔을 때 확인 순서

흐름의 어느 단계에서 멈췄는지부터 가리세요.
[보내는 데이터] → #BIZ_IN → SP → #BIZ_OUT → [받는 데이터] → 화면
1. SSMS 에서 SP 가 읽고 쓰는 테이블을 직접 SELECT 해 데이터가 맞는지 보세요.
2. Studio 디버거 패널에서 그 서비스의 [보내는 데이터] 실제 값, 메시지, 호출·결과 시각을 확인하세요.
3. 보낸 값에 _SUID 와 사용자 데이터만 보이면 보낼 섹터에 아직 값이 없는 시점입니다.
4. 서버 응답 원문이 필요하면 브라우저 F12 Network 탭에서 그 요청의 Response 를 보세요.
5. 설정 하나를 바꿔서 됐다면, 같은 조건에서 그 값만 되돌려 다시 확인한 뒤 원인으로 정하세요.

밖으로 공유할 때는 살아 있는 로그인 정보가 든 F12 의 Request Headers 와 Cookie 를 가리세요.
연결 오류, 방화벽, 인증서, ERP 공통 SP 문제는 오류 문구 전체, 앱 이름, 테넌트, 서비스 이름, 재현 순서를 담아 플렉스튜디오 담당자에게 문의하세요.
